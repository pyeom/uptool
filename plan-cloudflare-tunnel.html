Cloudflare Tunnel como modo opcional en uptool

Exponer uptool sin IP estática ni port forwarding, dejando el modo local actual intacto y como default.

Fecha 11 ago 2026 Esfuerzo 4–6 días Enfoque Full managed sin API token

Contexto

Hoy uptool exige tres cosas del usuario: un dominio propio, un registro DNS wildcard apuntando a la IP pública de su máquina, y port forwarding en el router. Eso deja fuera a cualquiera detrás de CGNAT o con IP dinámica, y obliga a exponer un puerto a internet. El README ya menciona Cloudflare Tunnel, pero solo como nota al pie, sin ninguna integración.

El objetivo es convertirlo en un modo de exposición de primera clase, seleccionable con tunnel = "cloudflare" en config.toml, que además trae HTTPS gratis — lo cual corrige de paso la debilidad conocida de --protect (Basic Auth sobre HTTP plano viaja legible). El modo local sigue siendo el default y no pierde ninguna capacidad: con tunnel = "none" (valor por defecto) el daemon se comporta exactamente como hoy y no spawnea ningún proceso extra.

La decisión de arquitectura que hace esto barato: uptool rutea por subdominio (x7k2mq.mydev.com). Un named tunnel con ingress wildcard preserva ese modelo tal cual, así que public.ts, ws.ts y todo el storage quedan sin tocar en su lógica de routing.

Opciones evaluadas

Full managed sin API token Elegida

uptool gestiona el ciclo completo: consigue el binario vía la dependencia npm cloudflared, crea el named tunnel con el cert.pem que genera cloudflared tunnel login, escribe el YAML de ingress, intenta registrar el DNS wildcard y cae a instrucciones manuales si Cloudflare lo rechaza, y corre cloudflared como proceso hijo supervisado del daemon. Ningún API token de Cloudflare se guarda en disco: la única credencial es el cert.pem que cloudflared ya maneja en ~/.cloudflared/.

StackTypeScript, Node ≥18. Nueva dep: cloudflared (npm). Binario cloudflared del sistema si ya está en PATH. Sin SDK de Cloudflare.
Esfuerzo4–6 días
RiesgosEl wildcard puede requerir un paso manual en el panel. La dep npm descarga un binario en tiempo de ejecución. Un cloudflared que crashea en loop no debe arrastrar al daemon.
TechoUn tunnel, un origen, sin réplicas ni alta disponibilidad. Requiere que base_url sea el dominio apex (límite de Universal SSL). No cubre quick tunnels ni usuarios sin dominio.

Wrapper delgado

Idéntico en arquitectura, pero uptool no se hace cargo del binario: exige cloudflared en PATH y falla con instrucciones de instalación si no está.

Esfuerzo1–2 días
RiesgosBajos. El onboarding depende de que el usuario instale bien el binario para su plataforma.
TechoUn paso manual más antes del primer deploy, y soporte desparejo entre plataformas.

Descartada porque: se eligió priorizar el onboarding de un comando. Igualmente su núcleo queda absorbido: si hay un cloudflared en PATH, se usa ese y la descarga npm nunca ocurre — así que en la práctica esta opción es el camino rápido dentro de la elegida.

Solo config + docs

Sin spawn ni comandos nuevos. Solo las claves de config que el modo tunnel necesita (bind, scheme, trust_proxy), soporte de CF-Connecting-IP, y un uptool tunnel print-config que emite el YAML para que el usuario lo corra con su propio systemd.

StackTypeScript, sin dependencias nuevas
Esfuerzo3–4 horas
RiesgosPrácticamente ninguno
TechoSin ciclo de vida gestionado, sin health integrado en status, sin creación de tunnel. El usuario coordina dos servicios a mano.

Descartada porque: es la Fase 1 del plan elegido, no una alternativa. Se entrega igual, como primer paso independiente.

Diseño

Claves de config nuevas

tunnel = "none"              # "none" | "cloudflare" — default "none": comportamiento actual
tunnel_name = "uptool"       # nombre del named tunnel
tunnel_id = ""               # UUID, escrito por `uptool tunnel setup`
tunnel_metrics_port = 20241  # metrics server de cloudflared, para /ready
cloudflared_path = ""        # override; vacío = PATH, luego binario del paquete npm
bind = "0.0.0.0"             # "127.0.0.1" cuando el tunnel está activo

~/.uptool/cloudflared.yml generado

tunnel: <UUID>
credentials-file: ~/.cloudflared/<UUID>.json
ingress:
  - hostname: "*.mydev.com"
    service: http://127.0.0.1:3000
  - service: http_status:404

Superficie CLI

uptool tunnel login    # passthrough a `cloudflared tunnel login` (genera cert.pem)
uptool tunnel setup    # crea tunnel, escribe YAML, registra DNS, actualiza config.toml
uptool tunnel status   # /ready del metrics server + `cloudflared tunnel list`
uptool tunnel off      # vuelve a tunnel = "none" y restaura bind/scheme locales

Fuera de alcance

  • Quick tunnels (trycloudflare.com): no soportan wildcard, requieren routing por path. Feature separada.
  • Routing por path en general (/<slug>/) — toca public.ts, el script de live-reload y las URLs relativas de los bundles.
  • Cloudflare Access / validación de JWT como reemplazo de Basic Auth.
  • Creación del registro DNS vía API token de Cloudflare (decisión explícita: sin tokens en disco).
  • Tunnels remotos gestionados desde el dashboard (modelo token-based).
  • Múltiples tunnels, réplicas o alta disponibilidad.
  • Windows como plataforma verificada: el spawn y el kill se escriben portables, pero CI solo cubre Linux.
  • Migración automática de deployments existentes de http:// a https:// — las URLs ya entregadas cambian de esquema. Se documenta, no se automatiza.
  • Auto-detección de que el usuario ya tiene un cloudflared corriendo por su cuenta para el mismo dominio.

Riesgos abiertos

  • El wildcard DNS puede ser rechazado por route dns — es el riesgo mejor documentado (Coolify, Dokploy). Mitigación: ya está en el plan como fallback de primera clase, con el CNAME exacto impreso y verificación por resolución DNS antes de dar el setup por bueno.
  • Universal SSL cubre un solo nivel de wildcard — si base_url es apps.mydev.com, los certificados no cubren x7k2mq.apps.mydev.com. Mitigación: validar en setup y advertir con la salida concreta (usar el apex, o Advanced Certificate Manager).
  • cert.pem es una credencial de alcance amplio sobre la zona — permite crear tunnels y registros DNS. uptool no lo copia, no lo mueve y no lo loguea; queda donde cloudflared lo pone. Documentarlo en la sección de seguridad del README.
  • QUIC sobre UDP 7844 bloqueado en algunas redes — mitigación: exponer --protocol http2 como opción de config cuando el tunnel no logra conectar.
  • Descarga de binario en tiempo de ejecución — la dep npm baja cloudflared en el primer uso. Mitigación: preferir siempre el binario de PATH, y que la descarga sea un paso explícito y anunciado, nunca silencioso durante serve.
  • Cobertura de tests en src/commands/* — ya se sabe que marca 0% porque la ejecución real pasa por subprocesos. Los tests de tunnel van por cli.test.ts con un cloudflared falso en PATH, siguiendo el patrón existente del repo.
  • Doble fuente de verdad en la config — setup reescribe scheme, trust_proxy y bind. Si el usuario los edita a mano después, el modo tunnel puede quedar incoherente. Mitigación: tunnel status detecta y reporta la incoherencia en vez de corregirla en silencio.
